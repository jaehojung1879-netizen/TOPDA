# 가이드 본문 직접 수정 — 설계안

> 목적: 조명·주담대 같은 **가이드 페이지의 문구를 브라우저에서 직접 고치고 저장**한다.
> 오타·뉘앙스·수치 갱신을 매번 개발 요청으로 처리하지 않기 위한 것이다.
>
> 상태: **설계안**. 아직 구현하지 않았다. 게시판 에디터(2026-07)는 별개로 완료돼 있다.

---

## 1. 왜 게시판처럼 간단하지 않은가

게시판 글은 Supabase의 `body` 한 칸에 들어 있는 **텍스트**다. 그래서 수정이 쉽다.

가이드 페이지는 다르다.

- `site/interior/lighting.html` 은 저장소에 커밋된 **정적 HTML 700여 줄**이다.
- 안에 표·인라인 SVG 도식·체크리스트·FAQ·구조화 데이터(JSON-LD)가 섞여 있다.
- GitHub Pages가 저장소 내용을 그대로 서빙한다. 브라우저에서 고쳐도 **저장할 곳이 없다.**

그리고 이 사이트의 핵심 제약이 하나 더 있다.

> **검색 노출이 사업의 전부다.** 본문을 자바스크립트로 나중에 끼워 넣는 방식은
> 정적 HTML보다 색인이 느리고 불안정하다. 어떤 방식을 쓰든 **최종적으로 서빙되는
> HTML 안에 글자가 그대로 들어 있어야** 한다.

이 두 가지가 설계를 거의 결정한다.

---

## 2. 후보 세 가지

### A. GitHub API 직접 커밋 (Decap/Netlify CMS 방식)

`/admin/` 페이지가 GitHub Contents API로 파일을 읽고, 고친 뒤 커밋한다.

- 장점: 저장소가 단일 진실. 정적 HTML 그대로라 SEO 영향 0. 되돌리기는 git이 해준다.
- 단점: **브라우저에 GitHub 쓰기 토큰을 둬야 한다.** fine-grained PAT을 이 저장소의
  `contents:write` 로만 좁혀도, localStorage에 있는 이상 유출 시 저장소를 쓸 수 있다.
  제대로 하려면 OAuth 중개 서버가 필요한데 그러면 서버가 생긴다(지금은 서버가 없다).

### B. Supabase에 덮어쓰기 저장 → 런타임에 치환

수정본을 Supabase에 넣고, 페이지가 열릴 때 JS로 문단을 바꿔치기한다.

- 장점: 즉시 반영. 이미 있는 인프라(Supabase + 운영자 키)로 끝난다. 토큰 문제 없음.
- 단점: **서빙되는 HTML에는 옛 문구가 남는다.** 검색엔진이 보는 것과 사람이 보는 것이
  달라진다. 이 사이트에서는 받아들이기 어려운 단점이다. → 단독으로는 탈락.

### C. Supabase 저장 + 빌드 때 HTML에 굽기 ← **권장**

B로 저장하되, **배포 워크플로가 그 수정본을 HTML 파일에 실제로 써 넣고 커밋**한다.

```
브라우저에서 수정
  → Supabase content_overrides 에 저장 (운영자 키로만)
  → 다음 배포(또는 즉시 수동 실행) 때 Action이:
      ① 미반영 override 를 읽어
      ② 해당 HTML 파일의 해당 블록을 교체하고
      ③ 커밋 + 배포
      ④ 반영된 override 는 applied 로 표시하고 비운다
  → 이후로는 저장소 HTML이 다시 유일한 진실
```

- 장점: 브라우저에 GitHub 토큰이 없다. 서빙 HTML은 항상 정적 = SEO 영향 0.
  저장소가 다시 단일 진실이 되어 내가 편집하는 흐름과 충돌하지 않는다.
- 단점: **반영까지 지연**이 있다(배포 1회, 수 분). 즉시 보고 싶으면 미리보기로 때운다.
- 완화: 편집 화면에서는 override를 즉시 얹어 보여 준다(운영자에게만). 방문자에게는
  구운 뒤에 보인다.

## 3. 권장안(C)의 구체 설계

### 3-1. 편집 가능 영역을 HTML에 표시한다

전체 WYSIWYG는 하지 않는다. 표·SVG 도식·JSON-LD까지 브라우저에서 만지게 하면
반드시 깨진다. **글자 블록만** 연다.

```html
<p class="g-lead" data-edit="lead">조명은 <strong>기구를 고르는 일이 아니라…</strong></p>
...
<p class="g-chapter-lead" data-edit="ch1.lead">등기구 상세페이지에서 봐야 할 값은…</p>
```

- `data-edit` 가 붙은 요소만 편집 대상이 된다.
- 키는 파일 안에서 유일하면 된다(`lead`, `ch1.lead`, `faq.3.a` 처럼).
- **표·SVG·체크리스트·카드에는 붙이지 않는다.** 구조 변경은 계속 코드로 한다.

한 페이지에 20~40개쯤 붙이면 "문구 고치기"의 90%가 커버된다.

### 3-2. 저장 형식은 게시판과 같은 마크다운-라이트

게시판 에디터에 이미 만들어 둔 것을 그대로 쓴다.

- 툴바: 굵게 · 기울임 · 링크 · 목록 · 인용 · 코드
- 저장은 텍스트, 렌더는 `renderRichText()`(DOM 직접 생성, `innerHTML` 미사용)
- 굽는 단계에서도 같은 규칙으로 HTML을 만든다 → **화면과 결과가 같다**

### 3-3. Supabase 스키마

```sql
create table public.content_overrides (
  id uuid primary key default gen_random_uuid(),
  page text not null,          -- 'interior/lighting.html'
  block text not null,         -- 'ch1.lead'
  body text not null,          -- 마크다운-라이트 원문
  updated_at timestamptz not null default now(),
  applied_at timestamptz,      -- 빌드가 HTML에 구운 시각
  unique (page, block)
);
```

- 쓰기·읽기 모두 **운영자 키 검증 RPC를 통해서만**. 익명 정책은 만들지 않는다.
  (게시판의 `verify_admin_key` / `admin_*` 패턴 재사용)
- 방문자 페이지는 이 테이블을 아예 조회하지 않는다 → 로딩에 영향 0.

### 3-4. 굽는 스크립트

`_meta/apply_overrides.py` (신규)

1. `applied_at is null` 인 override를 전부 읽는다
2. `page` 로 파일을 열고, `data-edit="{block}"` 요소의 **자식만** 교체한다
   (요소 자체·클래스·속성은 건드리지 않는다)
3. 바뀐 파일을 커밋
4. 성공한 override에 `applied_at` 기록

`deploy-pages.yml` 의 **맨 앞**에 넣는다. 단지 페이지 생성보다 먼저 돌아야 하고,
실패하면 배포를 멈춘다(잘못 구운 HTML을 올리는 것보다 안 올리는 게 낫다).

### 3-5. 편집 화면

`site/admin/edit.html` — `<meta name="robots" content="noindex">` 필수.
sitemap에 넣지 않고, `check_en_routes` 대상에서도 제외한다.

- 편집 가능한 페이지 목록 (data-edit 이 있는 파일을 빌드 때 목록으로 뽑아 둔다)
- 페이지를 고르면 `data-edit` 블록들을 순서대로 나열
- 각 블록은 게시판과 같은 툴바 + 미리보기
- 저장 → Supabase, 상단에 "다음 배포 때 반영됩니다 (약 3~5분)" 안내
- 운영자 키가 없으면 아무것도 보이지 않는다

## 4. 작업 규모

| 단계 | 내용 | 규모 |
|---|---|---|
| 1 | `content_overrides` 테이블 + 운영자 RPC (SQL) | 작음 |
| 2 | `apply_overrides.py` + 워크플로 배선 | 중간 |
| 3 | `site/admin/edit.html` + 편집 JS (게시판 에디터 재사용) | 중간 |
| 4 | 주요 가이드 20여 편에 `data-edit` 부착 | 중간 (기계적) |
| 5 | 되돌리기 UI (git 이력 대신 override 이전 값 1단계 보관) | 작음 |

게시판 에디터를 이미 만들어 뒀기 때문에 3번의 절반은 재사용이다.

## 5. 하지 않기로 한 것

- **전체 WYSIWYG** — 표·SVG·JSON-LD가 섞인 페이지에서는 반드시 깨진다.
  구조 변경은 코드로 남긴다.
- **브라우저에 GitHub 토큰 저장** — 유출 시 손해가 저장소 전체다. 굳이 감수할 이유가
  없다(C안이 같은 결과를 토큰 없이 낸다).
- **런타임 치환만 하는 방식(B 단독)** — 검색엔진이 보는 HTML과 사람이 보는 화면이
  갈라진다. 이 사이트에서는 치명적이다.
- **새 페이지 생성** — 새 가이드는 계속 코드로 만든다. 이 도구는 **고치기 전용**이다.
