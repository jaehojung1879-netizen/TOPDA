## 2. Single Source of Truth 감사 결과

### 감사 전 구조상의 문제

1. **`dsr.html` 이 DSR 산정만기를 직접 들고 있었다.** `rates.js` 의
   `dsr.applicability.assumedTermYears` 에 같은 표가 있는데, 페이지는 `a / 8`, `a / 5`
   같은 리터럴을 자기 코드에 적어 두고 있었다. `rates.js` 를 고쳐도 이 화면만 옛 값으로
   남는 구조였다.
2. **`registration-cost.html` 이 비주택 취득세율 4.6% 를 하드코딩**하고 있었다
   (`price * 0.04`, `price * 0.002`, `price * 0.004`). `rates.js` 에 `acquisitionTax.nonHouse`
   가 이미 있었다.
3. 검증 스크립트마다 `app.js` 를 **문자열 슬라이스**로 잘라 쓰고 있어, 스크립트별로
   잘라 오는 범위가 달라질 수 있었다.

### 감사 후 구조

```
법령·감독규정 원문
        ↓
site/assets/rates.js          ← 수치·시행일·근거·status 한 곳
        ↓
site/assets/app.js            ← 공통 calculation engine
        ↓
┌──────────────────┬──────────────────┐
개별 계산기 페이지        종합계산기
└──────────────────┴──────────────────┘
        ↑                     ↑
   scripts/check_calc_parity.mjs 가 두 갈래가 갈리지 않게 막는다
```

- `scripts/lib/calc_engine.mjs` — 모든 검증 스크립트가 **같은 방식으로 같은 코드**를
  로드한다(중괄호 짝 파싱). 문자열 슬라이스 방식을 대체.
- `scripts/check_calc_parity.mjs` 의 **구조 테스트**가, 계산 로직을 자기 페이지에 다시
  들고 있는 파일이 늘어나면 CI 에서 실패시킨다. 불가피한 경우 `ALLOWED_INLINE_CALC` 에
  **근거와 함께** 등록해야만 통과한다.

## 3. 감사 결과 — 계산기별 판정

### FIXED (명확한 오류를 발견해 공식 근거에 따라 수정)

#### F1. 취득세 6~9억 구간 — 법정 반올림 누락 · **HIGH**

- **근거** 지방세법 제11조 제1항 제8호 나목:
  > 세율 = (해당 주택의 취득당시가액 × 2 / 3억원 − 3) × 1/100
  > 이 경우 **소수점 이하 다섯째 자리에서 반올림하여 소수점 넷째 자리까지 계산**한다.
- **문제** 계산식은 구현돼 있었으나 **반올림 절차가 빠져 있었다.**
- **영향** 취득가액 7억원 주택:
  | | 세율 | 취득세 | 지방교육세 | 합계 |
  |---|---|---|---|---|
  | 수정 전 | 1.66666…% | 11,666,667원 | 1,166,667원 | 12,833,334원 |
  | 수정 후 (법정) | **1.67%** | **11,690,000원** | **1,169,000원** | **12,859,000원** |
  | 차이 | | +23,333원 | +2,333원 | **+25,666원** |
- **수정** `app.js: calcAcquisitionTax` 의 `progRate` 에
  `Math.round(x * 10000) / 10000` 추가.
- **고정** `tests/golden/acquisition-tax.json` 의 `acq_paid_700m_rounding`,
  boundary 테스트 「취득세 누진 구간의 법정 반올림이 실제로 적용된다」(5개 가격대).

#### F2. 양도세 장기보유특별공제 표1 — 소수 연수 보간 · **HIGH**

- **근거** 소득세법 제95조 제2항 [표1]은 「보유기간 **3년 이상 4년 미만** 100분의 6」
  처럼 **연 단위 구간표**다.
- **문제** `Math.min(0.30, holdYears * 0.02)` 로 소수 연수를 그대로 곱하고 있었다.
  취득일·양도일을 입력해 보유기간이 3.5년으로 계산되면 공제율이 **7%** 가 됐다(법정 6%).
- **영향** 공제가 과다 → **세액 과소 산출**. 양도차익 3억, 보유 3.5년 기준 약 200만원.
- **수정** `Math.floor(holdYears)` 로 정수 연수 판정.
- **고정** boundary 테스트 「장기보유특별공제 표1 — 연 단위 계단」에서 3.9년이 6% 인지
  명시적으로 검증.

#### F3. 양도세 보유·거주기간 — 응당일이 「1년 미만」으로 분류되던 오류 · **HIGH**

- **근거** 소득세법 제95조 제4항(보유기간은 취득일부터 양도일까지, 취득일 산입).
  국세청 해석상 2024-01-10 취득 → 2025-01-10 양도가 **정확히 1년**이다.
- **문제** 경과일수를 `365.2425` 로 나누고 있었다. 응당일(365일 경과)이 **0.9993년**이
  되어 「1년 미만」으로 분류됐다.
- **영향** 1년 경계는 세율이 **70% → 기본세율**로 바뀌는 자리다. 응당일에 양도한
  납세자가 70% 단기세율로 계산됐다. 2년 경계(60% → 기본세율, 1세대1주택 비과세 요건)도
  같은 오류.
- **수정** 응당일 기준 정수 연수 계산으로 교체.
- **고정** boundary 테스트 「양도세 보유 1년 경계 — 응당일 기준」·「2년 경계」.

#### F4. 양도세 1세대1주택 비과세 — 거주요건 미반영 · **HIGH**

- **근거** 소득세법 시행령 제154조 제1항 — **취득 당시 조정대상지역**에 있던 주택은
  보유 2년 외에 **거주기간 2년 이상**도 비과세 요건이다. 취득 후 조정대상지역에서
  해제됐더라도 취득 당시를 기준으로 판정한다.
- **문제** 계산기는 보유 2년만 보고 비과세를 적용했다. 조정지역에서 취득했으나 거주하지
  않은 1주택자에게 **세액 0** 을 표시했다.
- **영향** 가장 손해가 큰 방향의 오차(과세 대상을 비과세로 표시).
- **수정**
  - `calcTransferTax` 에 `acquiredInRegulatedArea` 입력 추가 → 참이면 `liveYears >= 2` 요구.
  - 한국어·영어 양도세 페이지에 체크박스 신설.
  - 판정 근거를 결과 화면에 노트로 노출(거주요건 미충족 시 경고, 비조정 가정 시 안내).
- **주의** 기본값은 `false`(취득 당시 비조정)로 두어 기존 동작을 바꾸지 않는다. 대신
  「비조정으로 보고 계산했다」는 안내를 항상 표시해 사용자가 판단하게 한다.
- **고정** boundary 테스트 「1세대1주택 비과세 — 취득 당시 조정대상지역이면 거주 2년 요건」.

#### F5. DSR 계산기 — 산정만기 상한 미적용 · **HIGH**

- **근거** 은행 여신업무기준 「DSR 산출시의 대출 연간 원리금 상환액 산정기준」
  (= `rates.js` 의 `dsr.applicability.assumedTermYears`):
  - 주담대 원금일시상환 … 대출기간(**최대 10년**)
  - 장기카드대출 … 약정만기 **3년 이내**(분할상환 구조 5년 이내)
- **문제** `dsr.html` 이 사용자 입력 만기를 **상한 없이** 그대로 나눗셈에 썼다.
  만기일시 주담대에 30년을 입력하면 연간 원금이 `대출액 ÷ 30` 으로 잡혔다.
- **영향** 연간 원리금 과소 → **DSR 과소 표시 → 대출 여력 과대 산출**. 3억원 만기일시
  주담대에 30년 입력 시 연간 원금이 1,000만원 vs 법정 3,000만원 — **2,000만원 과소**.
- **부수 오류** 「유가증권·기타담보대출」을 한 항목으로 묶어 둘 다 8년으로 처리했다.
  기준표상 유가증권담보는 8년, 기타담보대출은 10년이라 분리했다.
- **수정** `dsr.html` 이 `rates.js` 의 `assumedTermYears` · `creditAnnualizeYears` ·
  `securedLoanTerm` 만 읽도록 바꾸고, 상한을 실제로 적용.
- **고정** parity 테스트 「dsr 페이지가 산정만기 상한을 실제로 적용한다」.

## 4. Golden Dataset 구조

`tests/golden/*.json` — 7개 파일 / **64건**. 각 케이스가 갖는 메타데이터:

```jsonc
{
  "case_id": "acq_paid_700m_rounding",
  "effective_date": "2026-08-17",
  "boundary": "누진 구간 — 법정 반올림이 실제로 세액을 바꾸는 대표 케이스",
  "inputs": { "price": 700000000, "homes": 1, ... },
  "expected": { "baseRate": 0.0167, "acquisition": 11690000, ... },
  "tolerance": 1,
  "source": {
    "type": "LAW",                       // LAW | DECREE | RULE | REGULATION | NOTICE | …
    "title": "지방세법",
    "article": "제11조 제1항 제8호 나목 — 반올림 규칙",
    "effective_from": "2020-08-12",
    "effective_to": null
  },
  "verification_method": ["independent_reference_formula"],
  "confidence": "A",
  "verified_at": "2026-08-17",
  "note": "반올림 전 값은 0.016666…이며 …"
}
```

`scripts/check_golden_cases.mjs` 는 각 케이스를 **두 번** 검증한다.

1. **독립 Reference Formula 결과 === JSON 의 expected**
   → JSON 에 손으로 적은 값과 조문 구현이 서로를 검증한다.
2. **production 결과 === JSON 의 expected**
   → 실제 배포되는 계산기가 법령 기대값과 일치하는지.

①이 없으면 JSON 값이 어디서 왔는지 아무도 보증하지 않는다. ①·② 둘 다 있어야
「production 으로 expected 를 만드는 circular test」를 구조적으로 배제할 수 있다.

메타데이터 검증도 테스트가 강제한다 — `source.effective_from` 이 `effective_date` 보다
미래면 **케이스 자체가 실패**한다(시행 전 규정으로 만든 기대값 차단).

## 5. Independent Reference Formula

`scripts/reference/` — production 코드와 **의도적으로 다른 방법**으로 구현했다.

| 파일 | 대상 | production 과 다른 점 |
|---|---|---|
| `acquisition_tax_reference.mjs` | 취득세 | 조문 순서 그대로 분기, 감면 계산을 별도 함수로 분리 |
| `transfer_tax_reference.mjs` | 양도세 | 세액을 **구간별 적산**으로 계산 (production 은 「과세표준 × 한계세율 − 누진공제」). 누진공제표 오타까지 잡힌다 |
| `loan_reference.mjs` | 대출·DSR | 상환액을 **월별 시뮬레이션 + 이분법**으로 역산 (production 은 등비수열 폐쇄형) |
| `misc_reference.mjs` | 중개보수·전월세·인지세·청약 | 요율표를 **순회**해 판정 (production 은 if/else 분기) |

수밖에 없다. 각 파일 상단에 조문 근거를 함께 적어 명시적으로 관리한다.

## 8. 정책·법령 시점(versioning) 도입

`rates.js` 에 `RULE_STATUS` 어휘와 `isRuleApplicable(block, asOf)` 헬퍼를 추가했다.

| status | 뜻 | production 계산 적용 |
|---|---|---|
| `CURRENT` | 계산 기준일 현재 시행 중 | ✅ |
| `ENACTED_FUTURE` | 확정됐으나 시행 전 | `effectiveFrom` 이후 계산에만 |
| `PROPOSED` | 개편안·입법예고·국회 계류 | ❌ **절대 반영 안 함** |
| `EXPIRED` | 실효된 과거 규정 | 과거 시점 계산에만 |

24개 규정 블록 전부에 `status` 를 부여했다(현재 전부 `CURRENT`).
`upcoming: []` 배열을 신설해, 시행 전·개편안 정보는 **계산 데이터와 물리적으로 분리**했다.

`scripts/check_rule_versioning.mjs` 가 CI 에서 강제하는 것:

- 모든 규정 블록이 `status` + `effectiveFrom` + `source` 를 갖는가
- `status` 가 시행일·종료일과 모순되지 않는가 (`CURRENT` 인데 시행일이 미래 등)
- `PROPOSED` 규정이 계산 데이터 안에 있지 않은가
- `reviewedAt` 이 미래로 적혀 있지 않은가
- **`lastReviewed` 가 실제 블록 검증일을 넘지 않는가** — 「형식적으로 오늘 날짜로 바꾸기」 차단
- golden case 의 근거 시행일이 계산 기준일보다 미래가 아닌가

### Historical Rule Preservation

과거 규칙을 삭제하지 않고 보존하는 구조인지 테스트로 고정했다.

- 10·15 대책 이전 종전 규정(`loan.grandfather.priorRules`)이 남아 있는지
- 종전 값(시가 무관 6억, 스트레스 1.5%)이 현행 값(15/25억 구간, 3.0%)과 **다른지**
  — 한쪽이 덮어쓰이면 실패
- 경과규정이 **표시만이 아니라 계산에 실제로 반영**되는지
  (20억 주택: 현행 4억 vs 경과규정 6억)

`isRuleApplicable` 은 과거 기준일을 넣으면 그 시점의 `EXPIRED` 규정을 적용 대상으로
판정한다. 완전한 historical tax engine 은 이번 범위 밖이지만, 데이터 모델과 테스트
구조가 과거 규칙을 파괴하지 않도록 설계했다.

golden case 의 `confidence` 필드에 기록한다. 사용자 UI 에는 노출하지 않는다.

| 등급 | 뜻 | 해당 |

## 10. CI 연결

`.github/workflows/check-calculators.yml` 에 4단계를 신설했다. PR 에서
`site/assets/rates.js` · `site/assets/app.js` · `site/calculators/**` ·
`scripts/check_*.mjs` · `scripts/reference/**` · `tests/golden/**` 중 하나라도 바뀌면

- name: 규정 시점(status) 정합성 — 시행 전 규정이 계산에 섞였는지
  run: node scripts/check_rule_versioning.mjs

  run: node scripts/check_calc_boundaries.mjs

## 11. Invariant / Boundary 테스트가 막는 것

### Invariant 46건 (예시)

- 대출금액 ↑ → 연간 상환액이 줄지 않는다
- 금리 ↑ → 총이자가 줄지 않는다 (원리금균등·원금균등 각각)
- 상환기간 ↑ → 원리금균등 월 상환액이 늘지 않는다
- 같은 조건에서 원금균등 총이자 ≤ 원리금균등 총이자
- 필요경비 ↑ → 양도세가 늘지 않는다
- 취득가액 ↑ → 양도세가 늘지 않는다
- **세액이 양도차익을 넘지 않는다** (주택 수 × 보유기간 × 조정 여부 24조합)
- 한도는 LTV·가격대별·DSR 한도 중 어느 것도 넘지 않는다 (16조합)
- 취득가액 1억~20억을 2,500만원 간격으로 훑어 취득세가 단조증가하는지
- 전월세 전환의 **가역성** (전세→월세→전세가 원래 값으로)
- 청약가점이 84점·항목별 상한을 넘지 않는다 (240조합)

### 법령 자체가 불연속인 자리 — 예외 등록

무조건 연속성을 요구하면 계단식 규정을 오류로 잡는다. 그래서 **근거와 함께 등록된**
불연속만 허용한다.

| 불연속 | 근거 |
|---|---|
| 가격대별 한도 15억 / 25억 경계 | 금융위 「대출수요 관리 방안」(2025.10.15) 구간별 정액 한도 |
| 취득세 다주택 중과 진입 | 지방세법 제13조의2 제1항 — 표준세율 → 8% 정률 전환 |
| 양도세 단기보유 세율 1년·2년 | 소득세법 제104조 제1항 계단식 |
| 중개보수 구간 한도액 | 공인중개사법 시행규칙 [별표1] |

등록되지 않은 불연속은 실패로 처리된다. 취득세 6억·9억 경계는 **연속이어야 하므로**
1원 차이로 1만원 넘게 튀면 실패시킨다.

## 12. 시행 전 정책이 계산에 섞여 있었는가

**아니오.** 24개 규정 블록 전부의 `effectiveFrom` 을 확인했고, 계산 기준일(2026-08-17)
이후 시행되는 규정은 없었다. `PROPOSED` 상태의 항목도 없었다.

다만 **구조적으로 막을 장치가 없었다** — 발표·입법·시행을 구분하는 어휘가 아예
없었으므로, 누군가 개편안 수치를 넣어도 아무것도 잡히지 않았다. §8 의 status 모델과
`check_rule_versioning.mjs` 가 그 구멍을 막는다.

지방 비규제 스트레스 DSR 2단계 유예(`effectiveFrom: 2026-07-01`,
`validUntil: 2026-12-31`)는 감사 시점에 유효 기간 안이라 `CURRENT` 다. 2027-01-01
이후에는 `check_rule_versioning.mjs` 가 「CURRENT 인데 종료일이 지남」으로 실패시킨다.

## 15. 안전장치 — 지원 범위 밖 명시

이번 감사에서 새로 명시한 것:

- **양도세 비과세 거주요건** — 취득 당시 조정대상지역 여부를 사용자가 고르지 않으면
  「비조정으로 보고 계산했다」고 항상 안내한다. 조용히 비과세를 적용하지 않는다.
- **DSR 예적금·보험약관 담보대출** — 「이 대출을 새로 받을 때는 DSR 규제 대상이 아니지만,
  다른 대출을 신청하면 기존 부채로는 산입됩니다」를 항목 설명에 명시.
- **마이너스통장** — 「사용액이 아니라 약정 한도가 기준」임을 명시.
- **RTI** — `confidence: 'guideline'` 로 낮추고 「법정 한도가 아니라 감독당국
  여신심사 가이드라인」임을 데이터에 기록.

기존에 이미 명시돼 있던 것(재개발 조합원 취득 개략 추정, 부담부증여 분리, 지방 미분양
조례 미확인, 전세대출 상환능력별 근사, 장래소득 미반영 등)은 유지했다.

## 16. 테스트가 커버하지 못하는 영역

정직하게 남긴다.

1. **1차 출처 원문 대조의 한계.** 이 감사가 수행된 환경은 `law.go.kr` ·
   `nts.go.kr` · `wetax.go.kr` · `fsc.go.kr` 로의 아웃바운드 접근이 차단돼 있었다.
   조문 확인은 검색으로 회수한 **조문 인용문** 대조로 했고, 원문 전문(全文)을 열어
   확인하지 못했다. **배포 전 각 조문을 국가법령정보센터에서 눈으로 한 번 더 확인할 것.**
   특히 F1(반올림 규칙)·F4(거주요건)는 세액을 크게 바꾸는 수정이므로 우선 확인 대상이다.
   이 한계는 `rates.js` 의 `audits[0].limitation` 에도 기록했다.
2. **공식 계산기 직접 대조 없음.** 위택스·홈택스 계산기에 자동 접근할 수 없었다.
   금융위 공표 예시 재현(§6)이 유일한 기관 수치 교차검증이다.
3. **상속·증여세** golden case 없음 — 배우자 상속공제가 가족 구성·분할 방식에 따라
   달라져 단일 정답을 만들 수 없다(R4).
4. **DOM 렌더링 검증 없음.** 테스트는 계산 함수와 페이지 인라인 함수를 `node:vm` 에서
   직접 부른다. 「입력칸은 생겼는데 그 값을 읽는 코드가 없는」 부류의 배선 오류는
   구조 테스트(입력 존재 여부 검사)로만 부분 커버된다.
5. **지역별 조례.** 중개보수 상한요율은 시·도 조례 사항인데 서울 기준 표만 검증했다.
   다른 시·도는 「조례 미대조」 경고가 붙는 기존 구조를 유지했다.
6. **비교과세(R2)·법인·비거주자·특수관계인 거래**는 계산기 지원 범위 밖이며 테스트도 없다.
7. **국민주택채권 할인율**은 매일 변동하는 시장값이라 golden case 대상이 아니다.
   기존 `probe-bond-rate.yml` 워크플로가 수집한다.

## 17. 앞으로 이 체계를 쓰는 법

**세율이 바뀌었을 때**

1. `rates.js` 의 해당 블록을 고치고 `status` · `effectiveFrom` · `source` · `reviewedAt` 갱신
2. 옛 규칙은 지우지 말고 `status: EXPIRED` + `effectiveTo` 로 남긴다
3. `tests/golden/*.json` 에 **새 시행일 기준 케이스를 추가**한다 (옛 케이스는 그대로 둔다 —
   `effective_date` 가 다르므로 공존한다)
4. `scripts/reference/` 의 독립 구현도 조문에 맞춰 고친다
5. `node scripts/check_golden_cases.mjs` 로 ①reference ②production 둘 다 통과하는지 확인

**계산식을 고쳤을 때**

- 테스트가 실패하면 **expected 를 고치지 말고 계산식을 다시 본다.** expected 는 법령에서
  왔고 계산식은 코드에서 왔다. 법령이 실제로 바뀐 게 아니라면 틀린 쪽은 코드다.

**새 계산기를 만들 때**

- 계산 로직은 `app.js` 에 함수로 두고 페이지는 호출만 한다 (parity 구조 테스트가 강제)
- `tests/golden/` 에 근거 메타데이터를 갖춘 케이스를 최소 3건 만든다
- 경계가 있으면 `check_calc_boundaries.mjs` 에 (직전 / 정확히 / 직후) 세 점을 추가한다
